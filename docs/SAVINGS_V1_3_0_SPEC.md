## 2. Authorities, dates and event effects

ILS only for v1.3.0. All new monetary storage is finite `NUMERIC(18,2)`, maximum `9999999999999999.99`; amounts are nonnegative magnitudes. No rounding of an invalid precision at the boundary: reject before casting to the constrained type. New command inputs are canonical ASCII decimal strings matching `^(0|[1-9][0-9]*)(\.[0-9]{1,2})?$`, checked for range; new output amounts have two fractional digits. Use the existing minor-unit utilities for Node totals, never float-convert a value that feeds a write. Existing unrelated numeric contracts are unchanged.

`transactions` remains the cash authority. Entries repeat the approved amount/date/source/category as immutable audit facts and must agree with the active transaction at commit. Those snapshots are never added to cash totals. `savings_entries` determines held Savings and realized earnings; `savings_accounts` holds configuration only. Opening is an event, not a second stored balance. No account balance cache, reporting table or materialized view.

All effective dates are strict Gregorian `YYYY-MM-DD`/PostgreSQL DATE, never timestamp-converted. Today comes from `timezone('Asia/Jerusalem', statement_timestamp())::date`. No future financial entry. `transaction_date`, not `charge_date`, controls existing cash/month reporting. Store both cash dates in audit snapshots; `charge_date` must also be a valid calendar date. Opening/tracking dates cannot be future; an optional goal/release date may be future.

| Posted event | Cash row | Held Savings delta | Realized interest | Budget treatment |
| --- | --- | ---: | ---: | --- |
| `opening` | None | +amount (zero allowed) | 0 | No funding or current-period deposit |
| `deposit` manual/import-linked/recurring | One expense | +amount | 0 | Ordinary Savings-category actual unless created by the funded-transfer command |
| `withdrawal` | One income | −amount | 0 | No automatic budget funding |
| `interest_capitalized` | None | +net amount | +net amount | No checking income or funding |
| `interest_payout` | One income | 0 | +net amount | No automatic budget funding |
| `occurrence_skip` | None | 0 | 0 | Explicit schedule decision, not a financial posting |
| Reverse an event | Void/correct/detach its cash as explicitly requested | Exact negative of original | Exact negative of original earnings | Compensate related Budget postings atomically when present |

A real withdrawal of previously capitalized interest is still a withdrawal, not newly earned interest. No automatic interest accrual, tax calculation, projected cash, bank execution or investment positions. Stored rate is descriptive. Corrections restate the original effective period; a real later refund/return is a new event on its actual date, not an audit reversal.

## 3. Exact new relations

All names below are in `public`. Unless marked nullable, columns are NOT NULL. Every FK uses `ON DELETE RESTRICT`; there is no cascade deletion of financial history. Identity columns are `BIGINT GENERATED BY DEFAULT AS IDENTITY`, backed by their normal sequences. No new enum type or auxiliary table is needed.

Plan amount/day/start/next-due must be all absent or all present. A disabled plan may keep an optional default source; automation requires it. Due dates equal the nominal day clipped to the last day of their month. Updates use expected account revision. Immediate config retries return the recorded result; a retry after an intervening config/entry change gets a stale-revision conflict, never reapplies old settings. Creation retries always use the unique creation key, with mismatched payload rejected. No mutable opening amount exists here.

Indexes in addition to PK and creation-key UNIQUE: `savings_accounts_status_id(status,id)`; partial `savings_accounts_due(next_due_date,id) WHERE status='active' AND auto_deposit_enabled`; partial `savings_accounts_payment_source(default_payment_source_id) WHERE default_payment_source_id IS NOT NULL`.

### 3.2 `savings_entries`

| Columns | Type/default | Constraint/purpose |
| --- | --- | --- |
| `id` | BIGINT identity | PK |
| `account_id` | BIGINT | FK `savings_accounts(id)` |
| `command_id` | UUID | Idempotency key shared by the rows of one atomic command |
| `command_index` | SMALLINT | >=0; UNIQUE `(command_id,command_index)` |
| `command_kind`, `command_fingerprint` | TEXT | Fixed command name from §6, nonempty normalized complete payload fingerprint |
| `event_kind` | TEXT | `opening`, `deposit`, `withdrawal`, `interest_capitalized`, `interest_payout`, `occurrence_skip` |
| `entry_action` | TEXT default `post` | `post` or `reverse` |
| `amount` | NUMERIC(18,2) | Finite, >=0; >0 except opening/skip; skip must be zero |
| `effective_date` | DATE | Financial date/cutoff, or skipped nominal due date |
| `source_kind` | TEXT | `opening`, `manual`, `existing_transaction`, `recurring`, `budget_surplus`, `schedule_control` |
| `transaction_id` | INTEGER nullable | The only cash relationship; FK `transactions(id)` |
| `cash_movement_type` | TEXT nullable | `expense` or `income`; audit snapshot |
| `cash_category_id`, `cash_payment_source_id` | BIGINT nullable | FKs to categories/payment sources; audit snapshots |
| `cash_charge_date` | DATE nullable | Audit snapshot |
| `reverses_entry_id` | BIGINT nullable | UNIQUE FK to an original posted entry |
| `reversed_by_entry_id` | BIGINT nullable | UNIQUE FK to its reversal; DEFERRABLE INITIALLY DEFERRED |
| `supersedes_entry_id` | BIGINT nullable | UNIQUE FK to the immediately replaced posted entry |
| `occurrence_month` | DATE nullable | First day of the nominal plan month |
| `occurrence_root_id` | BIGINT nullable | FK to the first claim of that occurrence; NULL on first claim |
| `scheduled_due_date` | DATE nullable | Captured nominal due date |
| `plan_revision` | BIGINT nullable | Captured revision >=0, not a deduplication key |
| `reason` | TEXT nullable | Trimmed <=2000; required for reversal, skip or replacement |
| `created_at` | TIMESTAMPTZ default `now()` | Immutable audit posting time |

Computed amounts are expressions in the summary/read RPC, not writable columns: action sign is +1 for post, −1 for reverse; held sign is +1 for opening/deposit/capitalized interest, −1 for withdrawal, 0 otherwise. Earnings sign is +1 for both interest kinds and 0 otherwise. Multiply by action sign and amount. Never sum transaction totals and these computed cash snapshots together.

Financial/audit fields are immutable. The **only permitted UPDATE** is setting a posted row's `reversed_by_entry_id` once, from NULL to its exact newly inserted reversal. A guard enforces this narrowly; this controlled pointer makes active-link uniqueness enforceable without a third table or mutable financial amount. DELETE/TRUNCATE are forbidden. A reversal cannot itself be reversed; restoration is a new posted replacement with a new command and `supersedes_entry_id`.

Additional exact constraints/indexes:

- `savings_entries_one_opening`: UNIQUE `(account_id)` WHERE event_kind='opening' AND entry_action='post' AND supersedes_entry_id IS NULL. One initial opening, including zero. Corrections form a single replacement chain; opening cannot simply be deleted.
- `savings_entries_active_cash`: UNIQUE `(transaction_id)` WHERE transaction_id IS NOT NULL AND entry_action='post' AND reversed_by_entry_id IS NULL. One live Savings effect for a cash row across all accounts.
- `savings_entries_occurrence_claim`: UNIQUE `(account_id,occurrence_month)` WHERE occurrence_month IS NOT NULL AND occurrence_root_id IS NULL AND entry_action='post'. This survives reversal/cancellation.
- `savings_entries_active_occurrence`: UNIQUE `(coalesce(occurrence_root_id,id))` WHERE occurrence_month IS NOT NULL AND entry_action='post' AND reversed_by_entry_id IS NULL. Immediate partial unique indexes require reversing the old active pointer before inserting its replacement, inside one transaction.
- `savings_entries_account_date(account_id,effective_date,id)` for balances/history; `savings_entries_cash_history(transaction_id,id)` WHERE transaction_id IS NOT NULL for audit and guards. The command-pair UNIQUE index serves command lookup; FK/UNIQUE reversal and replacement indexes serve chain traversal.
- `reverse` iff reverses_entry_id is present; reverse has no reversed_by/supersedes/occurrence fields. Deferred trigger verifies a mutual original/reversal pair, same account, event kind, source, amount, effective date and all cash snapshots. No self-reference or reversal-of-reversal.
- Replacement must reference a reversed post and retain its occurrence root/month when present. Normal correction records reversal and replacement in the same command. Explicit reinstatement may reference a previously cancelled/skipped post whose reversal was recorded earlier; it creates no second reversal. One replacement per original; further corrections replace the new post. Moving a nonscheduled event between accounts is allowed under both account locks. Moving a scheduled occurrence to another account is rejected; cancel then explicitly record a distinct unscheduled event.
- Post cash kinds require all five cash-link/snapshot fields; noncash kinds require all five NULL. Active cash snapshots must equal transaction amount, transaction_date, movement_type, category_id, payment_source_id and charge_date. Historical reversed snapshots retain old facts and are not compared with a corrected cash row.
- Occurrence fields (month, due date, plan revision) are all present together; only posted deposit/skip may hold them. Due date belongs to occurrence_month and is >= plan start captured by the accepted command. A replacement root must be a first claim for that same account/month. `occurrence_root_id` is absent without occurrence_month.
- `opening` uses source opening, cutoff date and no cash/occurrence; `occurrence_skip` uses source schedule_control; `budget_surplus` is a deposit with validated Budget provenance. A deferred account constraint requires exactly one active opening per account and checks all active balance prefixes.

### 3.3 `savings_account_summary` — the only new view

Ordinary, nonmaterialized, one row per account, including archived/zero-balance accounts. Group the entries once per account before joining configuration; no join fan-out through transactions or Budget items. Emit: `account_id`, `name`, `status`, `currency_code`, `tracking_start_date`, `revision`, `target_date`, `next_due_date`, `auto_deposit_enabled`, `plan_revision`; nullable text `target_amount`, `monthly_amount`, `annual_interest_rate`; two-decimal TEXT `opening_balance`, `current_balance`, `deposits_total`, `withdrawals_total`, `capitalized_interest_total`, `paid_out_interest_total`, `realized_interest_total`, and nullable `target_remaining`. Each event-kind total includes signed reversal effects. `target_remaining = greatest(target_amount-current_balance,0)`; absent amount yields NULL. No target completion lifecycle change. Deposit totals exclude opening and interest. Held totals include archived accounts, paid-out interest contributes earnings only.

Progress is a display-only ratio of actual balance to target (uncapped numeric label, optionally capped bar). Period flows use the entries' effective dates in a read RPC; this all-time view must not be mislabeled as monthly flows or total wealth. Bank/checking balances are not inferred from net transaction cash flow.

## 4. Cross-table integrity, category roles and permissions

Add nullable `categories.savings_role TEXT`: `deposit`, `withdrawal`, `interest_payout`. UNIQUE partial index on non-NULL role, regardless of is_active. Deposit requires type expense; other roles require income. Seed three explicitly named categories only if no role rows exist; do not promote existing categories by name/keywords or retroactively reinterpret their transactions. Their displayed Hebrew names/icons remain editable. Role/type becomes immutable while referenced in Savings history; deactivation preserves history, but prevents new events and surfaces a configuration error. The old Budget reserve is not a category role.

Every live Savings cash row must be ILS, positive exact two-decimal value, correct movement/role, valid payment source, `loan_id IS NULL`, no `loan_payments` row, no installment parent/children/count>1, no transaction items, zero/null discount, no LEGO/checkout relationship. Link existing/imported ordinary transactions explicitly by ID and expected fingerprint, then set the correct role category atomically. Inactive references can remain on history; new payments require active source/category. A non-Savings category correction explicitly detaches/reverses the Savings effect; it cannot leave an active Savings row attached to ordinary spending.

Use deferred constraint triggers on `transactions` and `savings_entries` to enforce the pairing at commit, including bare insert/update/delete attempts from an existing ingestion path. A BEFORE mutation guard rejects hard deletion of any transaction in Savings history. Add a `transaction_items` INSERT/UPDATE guard forbidding items for a Savings-role transaction or one with Savings history, including a detached row, and enforce the reverse direction during link. Role/type edits on categories have their own guard. No caller-controlled session variable counts as proof that a trusted command ran.

Protect the reverse Loan relationship with one new Savings integrity trigger on `loan_payments`, BEFORE INSERT/UPDATE. For a non-NULL transaction_id, lock the referenced cash row before validation and reject a Savings-role transaction, a voided transaction or any transaction with Savings entry history. For a changed link, lock implicated transaction ids in ascending order. Savings linking also locks/revalidates the cash row and rejects an existing loan_payments link, so either order of concurrent link attempts permits at most one accounting use. The Loan-side guard never creates Savings data, changes a loan balance itself, calls a Savings mutation or takes a Savings account lock. Existing loan accounting functions and summary triggers continue unchanged. No loan_payments column, index, grant or financial calculation changes are required. A detached former Savings cash row remains ineligible for Loan linkage; ordinary cash editing and the dedicated void path below remain available.

Cancellation retains a transaction tombstone. Add nullable `transactions.voided_at TIMESTAMPTZ`, `void_request_key UUID`, `void_fingerprint TEXT` and `void_reason TEXT`. The four fields are either all NULL or all present; the fingerprint is nonempty, and the trimmed reason is 1–2000 characters. Add partial UNIQUE `transactions_savings_void_request_key(void_request_key) WHERE void_request_key IS NOT NULL`. These fields are immutable after the one transition from live to voided; inserts must have all four NULL. They are audit/idempotency metadata, not another financial ledger. The dedicated detached-cash command stores its request UUID directly as void_request_key, so reuse against another transaction conflicts. A command that also has a financial/Budget receipt derives its subordinate void key deterministically from the owning command UUID and transaction id. Fingerprint the action, transaction id, expected cash fingerprint, reason and original Savings entry id when applicable. Keep the original command receipt behavior for commands that also post Savings entries.

Voiding active Savings cash must reverse its active entry atomically. A correction that changes paid-out interest to capitalized interest also voids its old income under the same rule. Voiding already-detached cash follows the separate command below and appends no second Savings reversal. Historical external IDs remain reserved. Ordinary unrelated transaction deletion continues unchanged. Restoring cancelled cash creates a new transaction/entry linked through supersedes_entry_id; it does not unvoid a tombstone. This preserves auditable FK links without fabricating a compensating income transaction.

Protected void fields are writable only by privileged command owners. In #38, normalize non-owner UPDATE privileges on transactions to column grants that preserve each existing grantee's previously allowed columns while excluding the four new protected fields; remove any table-level or inherited grants that would defeat that exclusion without widening access. Preserve pre-existing column access, RLS and ordinary application behavior. SECURITY DEFINER commands perform the protected update; the mutation guard independently enforces its valid final state. Existing Loan RPCs keep their explicit column assignments and do not gain a void action. New-row guards reject pre-voided inserts even through another ingestion path. Do not use a caller-settable session flag as authorization.

A cash-to-cash correction keeps the live transaction ID, appends an exact reversal plus replacement, and atomically changes the cash amount/date/source/category. A detach keeps the cash row live with a normal category and reverses only the Savings effect. A cash cancellation voids it and reverses the effect. These are distinct explicit commands/UI choices. Opening and noncash-to-noncash interest corrections have no transaction mutation.

The preceding same-ID rule applies to cash-to-cash corrections; the no-transaction rule applies to noncash-to-noncash corrections. For interest-type corrections, use this explicit atomic matrix. These are corrections of an incorrectly recorded event, not a new real-world movement of previously earned money.

| Original → replacement interest | Cash action | Ledger action |
| --- | --- | --- |
| payout → payout | Update the same live income transaction | Reverse the old payout; post replacement payout |
| capitalized → capitalized | No cash write | Reverse the old capitalization; post replacement capitalization |
| payout → capitalized | Void the original income with its audit receipt; create no cash row | Reverse payout; post capitalization |
| capitalized → payout | Create one new income using explicitly supplied valid cash fields | Reverse capitalization; post payout |

The replacement event_kind determines the required cash action; callers cannot choose an inconsistent combination. A cash target requires category/source/charge-date fields; a noncash target requires cash fields NULL. Apply expected revisions, exact amounts, stable event ordering, original/replacement date restrictions, closed-month rules, active references and full-prefix solvency before commit. A capitalization already consumed by withdrawals may prevent conversion to payout. For equal net interest 10, payout→capitalized changes live checking income by −10, held Savings by +10 and realized earnings by 0; the reverse conversion changes these by +10, −10, 0. Neither direction unvoids or detaches the original income. Opening remains an opening and an occurrence remains a deposit/skip; this matrix does not permit arbitrary conversion of those events.

After detach, a live ordinary transaction with Savings history can be edited within the existing historical restrictions and can be cancelled through `void_detached_savings_transaction`. It must have no active Savings link and a normal non-Savings category. It retains the direct-ILS, no-items/installments/discounts/Loan/checkout/LEGO shape; ordinary editing means scalar cash fields, not converting this audited cash row into another subsystem's transaction. Transaction and item guards enforce these history restrictions. The command takes a request key, expected transaction fingerprint and reason; revalidates cash/Budget history under the command locks; sets the protected void receipt once; and returns affected transaction/account/month ids for refetch. Held Savings, interest, prior entries and account revision stay unchanged. Same-key/same-payload retries return the stored void receipt even after the row is no longer live; mismatched reuse conflicts. Cancellation never creates a zero-valued Savings event or another reversal of the detached entry. Hard deletion remains forbidden. Reinstating a detached deposit must explicitly relink its still-live cash row; it cannot silently create duplicate cash. A previously voided row is restored only through a new cash row with the audited replacement relationship.

Enable RLS on both new tables; no anon/authenticated direct data policies or DML grants. Express authentication remains the user boundary in this single-user application. Revoke PUBLIC/anon/authenticated EXECUTE on all new functions; grant the listed public entry RPCs and the explicit read-only Budget helper exception below to service_role. Direct new-table writes are revoked from service_role; narrowly scoped SECURITY DEFINER commands own writes. New read RPCs/view access are service_role only. Sequences are not exposed to browser roles. Qualify relations, use `SET search_path=pg_catalog,public,pg_temp`, and ensure untrusted roles cannot CREATE in public. Do not weaken existing grants or claim tenant isolation. All other internal helpers and trigger functions are not directly executable by API roles. Integrity trigger functions that inspect protected Savings tables execute as narrowly scoped SECURITY DEFINER owners with the same fixed search_path and qualified relations; existing Loan callers need no new ledger grants. Trigger execution is not a public mutation entry point. Relevant PostgreSQL rules: [function security](https://www.postgresql.org/docs/current/sql-createfunction.html).

One explicit read-only exception to the helper EXECUTE restriction is `budget_actual_transactions(DATE,DATE)`: grant EXECUTE to service_role, revoke it from PUBLIC/anon/authenticated, and define it as a STABLE SECURITY DEFINER SQL function with the fixed search_path above and fully qualified relations. Its body is a SELECT of eligible live expenses only; it accepts date bounds, has no dynamic SQL and performs no writes. This lets the existing service_role callers SELECT the Budget views that invoke it without granting direct access to the new ledgers. View ownership does not supply the caller's function EXECUTE permission; see [PostgreSQL CREATE VIEW, Notes](https://www.postgresql.org/docs/current/sql-createview.html). All mutating internal helpers remain nonexecutable by API roles.

## 5. Opening, correction and occurrence rules

### Opening cutoff and solvency

Opening is the independently confirmed held balance **at the beginning of tracking_start_date**. Dates before it cannot be linked, deposited or backdated into Savings. A cash movement on the cutoff day is post-opening only if the owner confirms it is excluded from opening. Otherwise choose the next day's cutoff; do not guess. Existing older transactions stay cash history with no Savings entries. No migration derives opening from legacy reserve, historic deposits, target or loan balances.

Changing opening amount is an explicit audited correction; the tracking cutoff and opening date stay immutable. Require reason and expected revision, and replace the active opening. Reject changes that make any later balance negative. Fix an incorrectly chosen cutoff before accepting financial history; v1.3.0 does not move cutoffs across posted events. An empty account can be archived and recreated with the right cutoff; its zero opening/audit remains.

Validate every affected account using active posts (post and reversed_by NULL), opening first then `(effective_date,original_post_id)` for other posts. `original_post_id` is a computed ordering key: follow the immutable `supersedes_entry_id` chain to its first post, or use the post's own id when it has no predecessor. Do not store another balance/order table or use the replacement's new id as the tie-breaker. Validate chains as acyclic and preserve their root through repeated correction/reinstatement; an allowed account move retains that root. The active replacement's effective_date remains authoritative, so an intentional date change still reorders the event by date. New independent financial events receive their own order. Audit history can continue to display posting ids/created_at independently of this financial ordering.

Every prefix must be >=0 and every sum must fit NUMERIC(18,2). A reversal's backdated negative row is audit, not a new withdrawal ordered at the end of history. Active-post balance must equal sum of all signed ledger effects. Lock both accounts for a move and verify both complete histories. Example: opening 100, deposit 200, later withdrawal 250 gives 50; reducing deposit to 100 would create −50 at the withdrawal, so reject the whole cash+ledger correction. Reducing withdrawal to 150 first permits the deposit correction, resulting balance 50. No force-negative flag.

Same-day correction proof: opening 0, deposit 100 (id 2), then withdrawal 80 (id 3) has prefixes 0,100,20. Correcting the deposit to 150 with replacement id 5 keeps original_post_id 2, producing 0,150,70. Ordering by id 5 instead would falsely produce −80 before the replacement. Correcting that deposit to 70 must still fail because its valid order produces 0,70,−10. Exercise repeated replacements and actual date changes as well as this first replacement.

For ordinary Savings cash changes, an effective month with a recorded Budget close is blocked, as is a change that would alter already captured carryover/disposition provenance. Linking a historical transaction is allowed only if its Budget actual contribution is unchanged, cutoff permits it, and reference reclassification does not alter a closed month's categories; otherwise reject with a concrete historical-correction requirement. Pre-cutoff linkage is always rejected. Noncash interest/opening corrections can restate Savings history without rewriting Budget history, subject to solvency and reserve reconciliation. These are deliberate bounded v1.3.0 rules, not an unresolved historical repair implementation.

### Recurrence

One plan per account. Identity is `(account_id, nominal calendar month)`, not cash date, nominal day, request ID, schedule revision or amount. The first deposit or explicit skip claims that identity permanently. Corrections keep the root identity. A cancelled deposit stays claimed and cannot reappear through automation; the owner can explicitly reinstate it as a replacement. Concurrent manual/job requests for the same occurrence either return the existing matching deposit or reject a conflicting payload, never add another transaction.

Due date is `min(monthly_day,last_day_of_month)` in each month. A day-31 plan runs Jan 31, Feb 28 (29 in leap years), Mar 31. The first due date is the first such day on/after plan_start_date. A worker handles at most the oldest outstanding occurrence per account per invocation, and only if due <= Jerusalem today. Missed January processed February 3 records cash February 3 with January occurrence/due snapshots; it does not invent January cash. Subsequent eligible catch-up occurs on another invocation. Nothing future is posted.

Manual/imported cash can fulfill a due occurrence only through an explicit selection; date/amount similarity is never enough. Actual cash date may differ from due date, must be >= cutoff and <=today, and fulfillment must use the plan amount/source or explicit owner override captured in the command fingerprint. No early fulfillment of a not-yet-due occurrence in this release. Plain manual deposits without an occurrence do not advance a plan.

Posting/claim and next_due_date advancement happen in the same transaction. Next due is the next unclaimed month using the nominal day, not `cash_date + 1 month`. Failure rolls everything back. A zero-amount `occurrence_skip` entry records an explicit owner decision and reason; no cash or balance is changed. No silent skipping after downtime.

Pause/archive retains next_due_date and existing claim history; archive disables automation. Resume preserves overdue work. Financial schedule changes/clearing are blocked while unclaimed overdue occurrences remain: fulfill or explicitly skip them first. Changes apply to the first future unclaimed month and increment plan_revision, never create another identity in an already claimed month. Skips remain final for automation; explicit reinstatement replaces the skip with a deposit. Reaching a goal never archives the account or stops its plan. No schedule/job/interest table.

All account IDs and monetary inputs are validated without lossy numeric conversions. Request fingerprint includes action, every normalized field, explicit nulls and original entry/transaction/occurrence IDs, with stable key ordering.

For the interest matrix in §4, correct_savings_event derives update/create/void/no-cash from the original and replacement kinds. A conversion to payout creates cash; it does not implicitly link an unrelated existing transaction. Conversion to capitalized interest records the original income's protected void receipt. Existing-transaction reinstatement after detach must explicitly identify and fingerprint the still-live row; reinstatement after void creates a new row. Detached-cash cancellation has its own transaction receipt because it has no ledger effect; its idempotency does not require inventing a Savings entry. Replay checks precede current-state eligibility checks, so a successful void can be retried safely.

Commands allocate a UUID idempotency identity before attempting mutations. They serialize same-key attempts using a transaction advisory lock derived from the UUID; hash collisions merely serialize unrelated work. Posted command rows have contiguous command_index 0..n−1 and identical command_kind/fingerprint. Successful retry returns original row IDs and current state; a reused key with different payload is conflict. A no-op returns current state without a second effect. Future retries after reversals still return the originally recorded command, not a new posting. For Budget transfers use existing `budget_operations.request_key` plus a deterministic derived Savings command UUID; verify both receipts agree.

Lock order for every new mutating Savings entry point, including account creation/configuration that touches references: `transactions` table SHARE ROW EXCLUSIVE first; `budget_unused_balance_policies` SHARE ROW EXCLUSIVE when needed; legacy `finance_tracker_budget_savings` advisory lock if touching reserve/close; then affected budget_months ascending ID, budgets ascending ID, categories ascending ID, payment_sources ascending ID, savings_accounts ascending ID, and existing transactions ascending ID. Acquire the command-key advisory lock after the initial table locks and before row locks. Discover rows, then revalidate under locks; if the discovered set changed, abort/retry the whole command. Config/category/source changes for Savings use the same order. The coarse cash-table lock is deliberate for this single-user first release: it prevents concurrent raw imports or ordinary transaction writes changing an approved Budget candidate, and avoids a SHARE-to-write upgrade deadlock between two closers. Existing Budget commands already acquiring SHARE serialize with it. Do not acquire a Savings account lock and then call an existing Budget RPC that takes transactions SHARE.

The Loan-side integrity trigger is a guard within an existing Loan write, not another top-level Savings command. It locks the referenced transaction rows and rechecks eligibility without entering the Savings account/command lock sequence. Savings cash linking must take/revalidate that same transaction row before accepting a link. Use a locking statement followed by a fresh eligibility query under READ COMMITTED, including checks for loan_payments and Savings history after any wait; do not reuse a pre-lock result or a STABLE-function snapshot for this check. New Savings mutations require READ COMMITTED and reject unsupported isolation before writes with a retry instruction. The Loan guard remains VOLATILE; at stricter isolation, a concurrently changed cash row must produce a serialization failure rather than permitting a stale relationship. Verify both orders of Loan/Savings link contention, including direct service_role loan_payments writes; a trigger check made only before waiting for the cash row is insufficient. Detached-cash void uses the top-level sequence with its affected cash/Budget references and has no Savings balance mutation.

Preview takes no durable locks and is not authorization to skip revalidation. Apply re-reads account revision/archive, source/category/policy, exact cash fields, source lifecycle/actuals/funding, active operation links and all selected close candidates under the lock sequence, recomputes the fingerprint and rejects staleness atomically. Time limits/deadlocks (`40001`, `40P01`) cause a bounded whole-command retry with the same key; validation conflicts return actionable Hebrew errors. No external HTTP calls occur while DB locks are held. Lock semantics follow [PostgreSQL explicit locking](https://www.postgresql.org/docs/current/explicit-locking.html).

For commands with a ledger effect: insert reversal when applicable, retire the old active pointer, update/create/void/detach cash according to the explicit action matrix, insert the replacement/post, advance schedule when applicable, post Budget compensation if authorized, and validate deferred mutual links, stable-order full account prefixes and `budget_assert_reconciled` before commit. Detached-cash void changes only its transaction/receipt and validates the relevant Budget effects; it posts no ledger or schedule effect. Constraint triggers must inspect the final stored rows, not stale intermediate trigger NEW records. Errors leave zero partial financial or schedule effects.

Public mutations must return Hebrew messages with stable codes, including `SAVINGS_LINK_CONFLICT`, `SAVINGS_CUTOFF_VIOLATION`, `SAVINGS_INSUFFICIENT_BALANCE`, `SAVINGS_HISTORY_CORRECTION_BLOCKED`, `SAVINGS_OCCURRENCE_CLAIMED`, `SAVINGS_PLAN_OVERDUE`, `SAVINGS_REFERENCE_INACTIVE`, `SAVINGS_PREVIEW_STALE`, and `SAVINGS_EXACT_MONEY_REQUIRED`. Example: `לא ניתן לתקן את ההפקדה: התיקון ייצור יתרה שלילית לאחר משיכה מאוחרת יותר.` No raw SQL constraint names as the only user guidance.

## 8. Legacy reserve transition

Keep `budget_savings_entries`, `budget_savings_state` and existing reserve-funded deficit/unbudgeted resolution. UI names this **legacy Budget reserve**, distinct from named held Savings; do not add its balance to account totals/wealth. Existing policy `savings` continues its current noncash behavior until explicitly changed. No mass policy conversion, historical cash insertion, table retirement or fabricated backfill.

At account opening, require the owner to declare whether part of its independently confirmed opening balance is already represented in the legacy reserve. `p_legacy_overlap_amount` is explicit, default UI zero only after confirmation; require a reason/evidence note if positive. Unknown overlap blocks that account opening with a reconciliation message. Atomically record the independently entered opening O once and **retire R_overlap from available legacy reserve**, with `0 <= R_overlap <= min(O,current reserve)`. This retirement is not another deposit: it removes an overlapping funding claim. Create no cash and no monthly funding/movement. Use the existing Budget root structure with new type `savings_reserve_retirement`, a new kind on `budget_savings_entries` with negative delta, and an operation item pointing to the opening entry. The legacy row's required category_id is the stable Savings deposit-role category; source/destination budget/month IDs and movement_id are NULL. The root uses current month only as audit identity, not invented historical cash/funding. Skip retirement rows entirely for zero overlap; existing reserve entries require nonzero deltas.

Example: legacy reserve R=500; owner confirms bank Savings opening O=1200, of which300 overlaps that reserve. After opening: S=1200 (not1500), R=200, cash=0, F/A/U unchanged. The retained200 is explicitly still outside named held Savings. For zero overlap R stays500. For zero reserve only overlap0 is allowed. The declaration is not machine-verifiable bank evidence and must never be auto-derived from the two amounts.

Opening correction also reconciles the retirement under the legacy reserve lock. Require a preview of old/new opening and overlap; reverse the prior retirement and post the replacement atomically, with resulting R>=0, overlap<=new opening and valid account prefixes. Use matching reserve-retirement reversal entries and operation/item reversal links. Releasing a claim back to reserve is permitted only when the owner confirms it is actually available outside named Savings; no ordinary cash withdrawal automatically does that. Deleting/archiving an account does not return its opening to reserve. Same independently represented money must never be available through both a live retirement-adjusted reserve and a new named account.

The existing legacy ledger permits only one row per operation_id. Therefore an opening correction with both a retirement reversal and replacement uses two distinct Budget root operations with request keys deterministically derived from the one Savings correction UUID. The reversal root points to the old retirement root, its item points to the new opening reversal entry, and the replacement root/item points to the replacement opening. Both roots use the current audit month. Extend tree validation only for this cross-month noncash retirement reversal; it has no funding/movement rows and cannot reverse a cash transfer or reopen a month. Zero old/new overlap omits the corresponding operation, rather than inserting a zero ledger row.

There is no general cash-transfer-from-legacy-reserve endpoint in v1.3.0. If remaining legacy reserve supports a new manual deposit's budget, use the existing explicit reserve-funded deficit/no-budget resolution: R decreases, monthly F/A increase to cover the normal deposit actual. That is separate from the already-funded surplus transfer and must not apply its actuals exclusion. Existing reserve reversals still enforce available balance. Preflight captures reserve sum and immutable row fingerprints; postflight proves zero automatic row changes. User-performed reconciliation and acceptance are recorded separately from disposable test results.
